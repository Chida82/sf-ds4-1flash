# server-text-encoding Specification

## Purpose
Guarantees that every text the server sends to a client is valid UTF-8 JSON,
whatever byte sequence the model generated, while leaving valid text untouched.

## Requirements

### Requirement: Responses are valid UTF-8
Every HTTP response body and every server-sent event the server writes SHALL be
valid UTF-8, for every endpoint and response kind (chat, text completion,
responses, reasoning content, tool-call arguments), streaming or not, steered or
not.

#### Scenario: Model emits an invalid byte sequence mid-answer
- **WHEN** the generated tokens' bytes contain a lead byte not followed by its continuation bytes (for example `0xE2` then an ASCII byte)
- **THEN** the non-streaming response body decodes as strict UTF-8 and parses as JSON

#### Scenario: Answer cut inside a multi-byte character
- **WHEN** generation stops at `max_tokens` after a token that carries only the first bytes of a multi-byte character
- **THEN** the final response, and the last streamed delta of the same request, decode as strict UTF-8

### Requirement: Invalid subparts become U+FFFD
Each maximal invalid subpart of the generated bytes SHALL be replaced by one
U+FFFD (`EF BF BD`) in the serialized text, following the Unicode "maximal
subpart" practice; no other character is altered, removed or added.

#### Scenario: Truncated, stray, overlong, surrogate and out-of-range bytes
- **WHEN** the text holds an incomplete sequence, a stray continuation byte, an overlong encoding, an encoded surrogate, or a code point above U+10FFFF
- **THEN** each maximal invalid subpart appears as exactly one U+FFFD and the surrounding characters are unchanged

### Requirement: Valid text is passed through byte for byte
For text that is valid UTF-8 the serialized output SHALL be byte-identical to
the output before this change, and the generated tokens SHALL not change in any
case.

#### Scenario: Existing server tests
- **WHEN** the server unit tests and the parity oracle run
- **THEN** every response that was valid UTF-8 before is byte-identical, and greedy tokens are identical

### Requirement: Streamed and non-streamed text agree
For the same greedy request the concatenation of the streamed content deltas
SHALL equal the non-streamed content, including where a replacement occurred.

#### Scenario: Invalid sequence split across deltas
- **WHEN** an invalid sequence's bytes arrive in two consecutive tokens and the request streams
- **THEN** the concatenated deltas equal the non-streaming content of the same request

### Requirement: A replacement is reported
When a response needed at least one replacement the server SHALL log one stderr
line naming the request, the number of replaced subparts and the byte offset of
the first in the generated text; a response with none logs nothing new.

#### Scenario: Replacement logged once per response
- **WHEN** a response needed three replacements
- **THEN** exactly one log line reports 3 replacements with the first offset

### Requirement: The trace shows the generated bytes
With `--trace FILE` the server SHALL write each generated token's bytes exactly
as the model produced them, before any replacement, so a replaced subpart can be
traced to the tokens or to the server's text handling; the response is the same
with or without the trace.

#### Scenario: Trace classifies the cause
- **WHEN** the server runs with `--trace` and a response needed a replacement
- **THEN** the trace's generated bytes show whether the invalid subpart was already in the tokens' bytes

#### Scenario: Trace changes no output
- **WHEN** the same greedy request runs with and without `--trace`
- **THEN** both response bodies are byte-identical
